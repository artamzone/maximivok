# Текущее изменение: расширение справочника работ по смете

## Target / Dependents
- `workDefinitions`, `WorkStore`, `/api/works`, `public/works.js` и расчёты отопления, использующие `HeatingWorkPrices`.
- Потребители: страница работ, три веб-маршрута расчёта/сохранения, `calculateHeating`, сохранённые версии цен и отчётов.
- Источник новых строк — лист «Отопление» файла «Смета работ.xlsx»: 35 позиций отопления, включая строку «Штробление стен» с отсутствующей базовой ценой (по решению пользователя импортировать её как 0). Остальные листовые разделы не включать.
- Новая модель цены: редактируемая базовая цена; единая редактируемая наценка в %, 45% по умолчанию; цена ИВОК = `ceil(basePrice * (1 + markupPercent / 100))` за единицу справочника. Если пользователь подтвердит другую базу округления для отображаемой цены за единицу — скорректировать до реализации.

## Risk: High
Общий `workDefinitions` и `/api/works` используются в текущих расчётах отопления. Расширение цен и конфигурации не должно молча изменить применённые цены или исторические отчёты, а старый API с пятью ценами должен получить осознанную замену/миграцию совместимого JSON-хранилища.

## План / проверки
1. Регрессионные тесты на весь список 35 работ, 0 для пропущенной цены, изменение базовой цены/наценки и ceil на границах.
2. Версионированное хранение полного каталога, базовых цен и markupPercent; API/UI с вводом процента над таблицей, редактируемой базовой ценой и вычисляемой ценой ИВОК.
3. Сохранить согласованное поведение текущего отопительного расчёта. Из-за подтверждённого пользователя перехода на расширенный каталог проверить новые расчёты, старые отчёты, старые данные в work_price_versions и независимость от КП (которое отложено).
4. Полные тесты/typecheck, UI/HTTP на временной БД, документация и итоговый diff. Не менять рабочую БД и не перезапускать сервер.

## Уточнение границы формулы
- Пользователь подтвердил импорт всех работ с листа «Отопление», базовую редактируемую цену, общий editable процент наценки 45% и округление вверх итоговой суммы строки после умножения на количество. Значения из PDF — только демонстрационные.
- Сам справочник сейчас не вводит количество для каждой позиции. Реализуемая цена ИВОК за единицу будет отображаться как `basePrice * (1 + markupPercent / 100)` с точной денежной арифметикой; отдельное округление единицы нельзя делать, поскольку подтверждённое правило относится к итогу строки после умножения на количество. Округление строки будет реализовано/тестировано при появлении расчёта по количеству, не в этом подэтапе.
- Для отопительных расчётов нужно сохранить действующий контракт конечной цены монтажа ТП и утеплителя: применять редактируемую базовую цену без ИВОК-наценки (снимок справочника получает базовые `floor_heating` и `insulation`). ИВОК цены пока остаются для клиентского справочника, а применение к строкам КП отложено до отдельного согласования этапа КП.
- Список из книги имеет базовые цены и строку без цены. Пользователь требует отсутствующую цену импортировать как 0. Единицы исходником на листе «Отопление» не определены явно (в верхней таблице написано «ЦЕНА», «кол-во», нет колонки единиц), поэтому вне доменной семантики приложения отображать цену как «за ед.» и не вводить предположительные единицы. Определение единиц для расчёта КП отложить.
- Миграция истории: сохранять базовые цены и наценку в новых версиях; у прежних версий только конечные цены пяти работ — чтение и воспроизводимость отчётов сохранять. Изменение цены и/или процента создаёт новую версию; без изменений версия не создаётся.

# TASK-03: редактируемый справочник работ

## Согласовано
Пять работ из раздела 15 ТЗ; отдельная вкладка как материалы. Сохранённые цены ТП и утеплителя применяются к новым веб-расчётам. Старые отчёты неизменны. Водоснабжение, канализация и лежак пока только справочные позиции; 12 000 ₽ — базовая стоимость лежака, не цена погонного метра.

## Target / Dependents
- Чистый `calculateHeating`: дополнительный необязательный снимок двух расценок и версии справочника. Старый вызов и CLI сохраняют поведение с нормами config. HTTP передаёт текущий снимок, включая при создании объекта и добавлении версии.
- Потребители: server (3 маршрута), cli; calculator/partial/storage/server/materials/catalog-storage tests. Сохранение JSON отчёта не требует изменения старых записей.
- Новое хранилище на существующем SQLite-соединении: неизменные версии пяти цен, organization_id, атомарная запись, защита от перезаписи устаревшей вкладкой.
- Чтение стартовых цен из config без записи в БД; таблица создаётся только при первом сохранении справочника. Рабочую БД и сервер во время реализации не менять.
- Общая точная денежная арифметика выделяется из materials с сохранением прежнего экспорта.

## Risk: High
Общее расчётное ядро. Сохраняем прежний однопараметрический контракт и golden-тест; снимок и динамические коды расценок только при явно переданных ценах. Старые JSON читаются без миграции. Редактор инженерных норм не входит в этот шаг.

## План / проверки
1. HTTP-тест пяти начальных позиций (RED), затем хранилище и API. Цена — неотрицательное число с точностью до копейки; пустые, неизвестные поля/ID, дубли и переполнение отклоняются.
2. Интеграция снимка в три расчётных маршрута: проверка новых сумм, неизвестной длины контура, нуля с предупреждением, воспроизводимости и неизменности старой версии; сохранение после перезапуска; конфликт 409 и откат при ошибках.
3. Страница /works, редактирование только цен, кнопки сохранения/перезагрузки, защита несохранённого ввода и ошибок. Без новых зависимостей.
4. Полные тесты/typecheck, браузер на временной БД, HTTP smoke, документация и итоговый diff. Активация нового backend отдельно с разрешения пользователя.

## Результат проверки
81 тест, typecheck, JS syntax и diff-check прошли. Chrome: реальная новая вкладка, пять цен, сохранение/новый расчёт/старый отчёт, несохранённый ввод главной страницы, конфликт вкладок, подтверждение перезагрузки, ошибки сети, нулевая цена и 360 px. Повторно прошли браузерные проверки каталога, материалов и сводки. Все записи — только во временных БД; рабочий сервер не перезапущен.

Отдельное наблюдение: один промежуточный прогон старого HTTP-теста каталога получил `fetch: bad port` при выборе случайного порта. Два следующих полных прогона прошли; тестовую инфраструктуру портов в рамках этой задачи не меняли.
