# План реализации ИИ-агента ИВОК

## Зачем нужен этот документ

Разбить ТЗ версии 1.0 на небольшие проверяемые задачи. Сначала реализовать и проверить расчёт отопления, затем постепенно добавить остальные части MVP без лишнего усложнения.

## Принципы реализации

1. **Расчёты выполняет код, а не нейросеть.** ИИ только извлекает и объясняет данные.
2. **Начинаем с одного приложения.** Не использовать микросервисы, очереди и сложную инфраструктуру без реальной необходимости.
3. **Каждая задача даёт рабочий результат**, который можно показать инженеру.
4. **Неизвестное не выдумывается.** Результат получает статус: рассчитано, требует проверки или невозможно определить.
5. **Правила и цены меняются без правки формул.** Настраиваемые значения хранятся отдельно от расчётного кода.
6. **Инженер утверждает результат.** Неутверждённое КП нельзя отправить клиенту как окончательное.
7. **Источник каждого входного параметра сохраняется:** проект, клиент, предположение ИИ или инженер.

## Простая целевая архитектура

На этапе MVP достаточно:

- одного backend-приложения с API;
- одного простого веб-интерфейса инженера;
- одной реляционной базы данных;
- отдельного модуля детерминированных расчётов;
- адаптеров Telegram, WhatsApp, 1С и AI внутри того же приложения;
- генерации КП из сохранённого расчёта.

Не нужны на старте: микросервисы, Kubernetes, собственная BIM-система, полноценный CAD/3D-редактор и автоматическое инженерное проектирование.

Рекомендуемый минимальный стек для обсуждения перед разработкой: TypeScript, Node.js, PostgreSQL и простой web-интерфейс. Для локального прототипа TASK-01 база данных не требуется.

## TASK-01. Сделать расчёт отопления

**Цель:** получить отдельный проверяемый модуль предварительного расчёта отопления. Это первая и главная задача.

### Входит

- Входные данные в простой структурированной форме JSON:
  - площадь дома и помещений;
  - высота потолков;
  - наличие обычных и панорамных окон;
  - площадь тёплого пола;
  - наличие радиаторов;
  - тип источника отопления;
  - доступная электрическая мощность;
  - количество жильцов, ванн и душей.
- Расчёт тёплого пола:
  - 6 м трубы на 1 м²;
  - стандартный контур 80 м;
  - исключение до 90 м только с предупреждением;
  - округление количества контуров вверх;
  - один коллектор до 12 контуров;
  - равномерное деление на несколько коллекторов при количестве более 12;
  - смесительный узел только при совместной работе тёплого пола и радиаторов.
- Предварительный расчёт радиаторов:
  - 100 Вт/м²;
  - уменьшение на 30% при наличии тёплого пола;
  - панорамное окно переводит решение на проверку инженера.
- Предварительный выбор котла по таблице из ТЗ.
- Предварительный выбор бойлера по таблице из ТЗ.
- Выбор подходящего шаблона котельной из фиксированного списка.
- Расчёт стоимости известных работ: монтаж тёплого пола и укладка утеплителя.
- Понятный отчёт: входные данные, результаты, применённые правила, предупреждения и статус проверки.
- Частичный расчёт: каждый блок рассчитывается при достаточных данных, остальные показывают список недостающих параметров. Неизвестное значение не заменяется нулём или предположением.
- Для решений о радиаторах и бойлере различаются «есть/нужен», «нет/не нужен» и «неизвестно». Отсутствие данных не означает отсутствие оборудования.
- Простая веб-форма с помещениями и результатами; JSON используется для CLI, экспорта и тестов.
- Суммы обозначаются как «стоимость известных работ», а не полная стоимость отопления. Материалы без цены не считаются бесплатными.

### Не входит

- Полный теплотехнический расчёт теплопотерь.
- Автоматический подбор конкретных товаров из 1С.
- Генерация КП и общение с клиентом.
- Автоматическое решение для панорамных окон и домов более 400 м².

### Как реализовать просто

1. Создать чистые функции расчёта без базы данных и AI.
2. Вынести изменяемые нормы и цены в один конфигурационный файл.
3. Использовать существующие CLI и веб-форму; не добавлять новый клиентский фреймворк.
4. Для каждого результата сохранять код применённого правила и статус.
5. Любое отсутствующее правило возвращает запрос инженеру, а не приблизительное значение.
6. Сохранить статусы `calculated`, `requires_engineer_review`, `impossible`: недостаток данных даёт `impossible` соответствующему блоку, но не мешает рассчитывать остальные.
7. Согласовать расширение входного контракта для неизвестных значений. Старые корректные JSON и сохранённые расчёты должны оставаться читаемыми; меняются только необходимые поля.

### Критерии готовности

- Автоматические тесты покрывают границы 12/13 контуров, 80/90 м, 200/250/300/400 м².
- Пример 14 контуров делится как 7+7, 30 — как 10+10+10.
- Панорамные окна и неизвестные сочетания бойлера не рассчитываются молча.
- Повторный запуск с одинаковыми данными и правилами даёт одинаковый результат.
- Проверены случаи: отопление не описано; данные заполнены частично; наличие радиаторов/бойлера неизвестно; правило бойлера отсутствует; цены материалов отсутствуют.
- Пустые поля не превращаются в нули. Неопределённый бойлер не выводится как выбранный товар «1 шт.».
- Старый полный вход рассчитывается без изменения результата, старые сохранённые версии открываются.
- Инженер ИВОК проверил минимум 5 реальных примеров и подтвердил правила либо дал корректировки.

**Результат:** работающий прототип расчёта отопления, который можно проверить до создания всего приложения.

## TASK-02. Создать карточку клиента и объекта

**Цель:** сохранять исходные данные и результаты TASK-01 в одном простом приложении.

### Входит

- Клиент, объект, помещения и инженер.
- Значение параметра, его источник и статус проверки, включая зависимые и вычисляемые параметры. Источник и подтверждение независимы: данные из проекта могут быть непроверенными.
- Ручной ввод и редактирование данных инженером.
- Сохранение расчёта отопления и его предупреждений, включая частично рассчитанный объект и неизвестные значения. Сохранение карточки без расчёта остаётся доступным.
- Поле `organization_id` в основных сущностях для будущего разделения компаний без отдельной SaaS-платформы.

### Решения для локального этапа

- Приложение работает только локально на `127.0.0.1`; авторизация откладывается до размещения вне локального компьютера.
- Для хранения используется SQLite в локальном файле. Доступ к данным отделяется от HTTP-обработчиков, чтобы позднее перенести данные в PostgreSQL.
- Пока используется одна системная организация, но `organization_id` сохраняется для последующего разделения данных.
- Обязательные поля карточек: имя клиента и адрес объекта. Остальные поля могут быть пустыми.
- Правила расчёта будут уточняться, поэтому структура данных должна допускать добавление новых полей.

### Критерии готовности

- Инженер создаёт объект с именем клиента и адресом, вводит доступные данные и запускает расчёт отопления.
- Необязательные поля можно оставить пустыми.
- Данные после перезапуска не теряются.
- Видно, откуда получен каждый параметр.
- Основные сущности содержат `organization_id` для будущей изоляции данных.

### Отложенные улучшения интерфейса

- Просмотр истории версий расчётов с датой и статусом, открытие старой версии.
- Индивидуальное редактирование источника и статуса каждого введённого поля, без перезаписи метаданных остальных полей.
- Предупреждение о несохранённых изменениях при переключении объекта и создании новой карточки.
- Выбор существующего клиента для нескольких объектов без дублирования клиента.

**Зависит от:** TASK-01.

## TASK-03. Подключить материалы 1С и базу работ

**Цель:** использовать только реальные товары и редактируемые цены.

### Входит

- Импорт согласованного файла выгрузки 1С.
- Поля товара из ТЗ, розничная цена и дата обновления.
- Поиск и фильтрация примерно 5 000 позиций.
- Отдельный справочник работ с единицей и ценой.
- Ручной выбор инженером, если товар не найден.
- Журнал импорта с ошибками строк.
- Простой редактор разрешённых норм и цен. В версиях расчётов сохраняются применённые значения и версия правил; изменение настроек не переписывает старые результаты.

### Критерии готовности

- Повторный импорт обновляет позиции и не создаёт дубликаты.
- Ни товар, ни цена не создаются AI самостоятельно.
- Цены работ меняются через интерфейс без изменения кода.

**Зависит от:** TASK-02 и согласования формата выгрузки 1С.

## TASK-04. Сделать расчёты водоснабжения и канализации

**Цель:** добавить два детерминированных расчётных блока по правилам ТЗ.

### Входит

- Подсчёт ХВС, ГВС и рециркуляции по каждому прибору.
- Лучевая схема, труба PEX 16×2,2 и метраж по трассам.
- Подбор только существующих конфигураций коллекторов.
- Канализация 50/110 мм, точки, лежаки и уже выполненные закладные.
- Стоимость работ из базы работ.
- Предупреждение для рециркуляции душа и других отсутствующих правил.

### Критерии готовности

- Пример «ванна + раковина + унитаз» даёт 3 ХВС и 2 ГВС.
- Уже выполненные работы не попадают в расчёт повторно.
- Нестандартный коллектор не выдумывается.
- Все суммы используют актуальную базу работ.
- Без подтверждённых трасс можно посчитать точки, но не метраж. Показанные на скриншотах 118 м не являются эталоном без исходных замеров.
- Неизвестная рециркуляция не трактуется как подтверждённое отсутствие.
- До реализации согласовано, входит ли монтаж трапа в цену канализационной точки: одна работа не оплачивается дважды.
- Обозначение Ø100 в проекте не заменяется на Ø110 автоматически; требуется согласованное правило или подтверждение инженера.

**Зависит от:** TASK-02, TASK-03.

## TASK-05. Сформировать КП, согласование и версии

**Цель:** получить понятное коммерческое предложение с обязательной проверкой инженера.

### Входит

- Разделы: отопление, водоснабжение, канализация.
- Отдельные строки материалов и работ.
- Количество, единица, цена, сумма и общий итог.
- Черновик, утверждено, отклонено.
- Ручные правки инженера с комментарием.
- Версии v1, v2, v3 и список изменений стоимости.
- Экспорт утверждённого КП в PDF.

### Критерии готовности

- Неутверждённое КП нельзя отметить как готовое клиенту.
- Изменение создаёт новую версию и не стирает предыдущую.
- Видно, какие блоки и суммы изменились.
- PDF понятен клиенту и не выглядит как необработанная выгрузка 1С.
- Известная сумма, позиции без цены и полнота расчёта показаны отдельно. Неизвестная цена не равна нулю; неполная сумма не обозначается полной стоимостью.
- Неопределённое оборудование показывается как вопрос инженеру, а не выбранная товарная позиция.

**Зависит от:** TASK-01, TASK-03, TASK-04.

## TASK-06. Добавить Telegram и первичный опрос

**Цель:** автоматизировать сбор исходных данных через один канал и проверить сценарий общения.

### Входит

- Telegram-бот.
- Создание или поиск карточки клиента и объекта.
- Вопросы только по недостающим данным.
- Подтверждение извлечённых значений клиентом.
- Передача спорных вопросов инженеру.
- Ответы только по утверждённому КП после его отправки.

### Критерии готовности

- Бот не повторяет уже отвеченный вопрос.
- Ответ клиента сохраняется с источником «клиент».
- AI не выполняет математические расчёты самостоятельно, а вызывает расчётный модуль.
- Бот не отправляет черновик как окончательное КП.

**Зависит от:** TASK-02, TASK-05.

## TASK-07. Добавить PDF-проекты и фотографии

**Цель:** помогать инженеру переносить данные из файлов, не превращая AI-анализ в единственный источник истины.

### Входит

- Загрузка PDF и изображений.
- Извлечение предполагаемых помещений, площадей, приборов и котельной.
- Экран подтверждения найденных данных инженером.
- Ссылка каждого значения на файл/страницу и статус «требует проверки».
- Структурированный план объекта; изображение не используется как единственная геометрия.

### Критерии готовности

- Неподтверждённые AI-данные явно отмечены.
- Ошибка распознавания не изменяет утверждённый расчёт автоматически.
- Проверяется, какие сведения действительно есть в документе: дизайн-проект сам по себе не подтверждает отопительную схему или длины инженерных трасс.
- Инженер может исправить каждое найденное значение.

**Зависит от:** TASK-02.

## TASK-08. Подключить WhatsApp и сопровождение после КП

**Цель:** добавить второй обязательный канал после проверки сценария в Telegram.

### Входит

- Официальный WhatsApp API выбранного провайдера.
- Общая история сообщений независимо от канала.
- Отправка только утверждённых документов.
- Запрос изменений, создание новой версии и повторное согласование.
- Объяснение различий между утверждёнными вариантами оборудования.

### Критерии готовности

- Telegram и WhatsApp используют одну бизнес-логику.
- Повторное сообщение не создаёт дубль клиента или объекта.
- Изменение от клиента создаёт черновик новой версии КП.

**Зависит от:** TASK-05, TASK-06.

## TASK-09. Подготовить MVP к эксплуатации

**Цель:** проверить безопасность, восстановление и полный сценарий перед запуском.

### Входит

- Роли и разграничение доступа.
- Журнал действий и изменений.
- Резервное копирование и тест восстановления.
- Изоляция организаций на уровне запросов и базы.
- Обработка ошибок внешних API.
- Контроль затрат AI/API.
- Инструкция запуска и передачи проекта другому разработчику.
- Сквозная проверка: заявка → расчёт → КП → утверждение → изменение → новая версия.

### Критерии готовности

- Есть успешный тест восстановления резервной копии.
- Критические действия записываются в журнал.
- Чужие клиенты, правила и цены недоступны другой организации.
- Все обязательные сценарии MVP пройдены на тестовом объекте.

**Зависит от:** TASK-01–TASK-08.

Эти вопросы не должны блокировать TASK-01 целиком, но неизвестные правила должны возвращать статус проверки инженером:

1. Полная матрица бойлеров и правило рециркуляции душа.
2. Набор утверждённых шаблонов котельной и их материалы.
3. Правила расчёта труб и фитингов котельной.
4. Правила нестандартных панорамных окон.
5. Доступные конфигурации коллекторов.
6. Формат и частота выгрузки из 1С.
7. Полный справочник работ и актуальные цены.
8. Макет итогового КП.
9. Провайдер официального WhatsApp API.

## Порядок доработки уже реализованных TASK-01 и TASK-02

Прототип TASK-01 реализован; TASK-02 выполнен частично. Не начинать проект заново. Материалы в `От Максима/` — скриншоты, а не утверждённые исходные расчёты или код.

1. **Доработать TASK-01:** согласовать неизвестные значения во входе, обновить типы и валидацию, затем независимость расчётных блоков. Формулы отопления и существующие статусы сохранить.
2. **Доработать TASK-02:** разрешить сохранение нового частичного входа и его метаданных. Проверить чтение старых версий; не удалять SQLite и не пересчитывать историю автоматически.
3. **Обновить существующую форму:** убрать подмену пустых полей нулями, явно показывать неизвестные решения и необходимые уточнения. Примерные значения не сохранять как подтверждённые данные клиента.
4. **Повторить проверки TASK-01/02:** регрессионные тесты расчёта, HTTP/CLI и хранения; `npm test`, `npm run typecheck`; загрузка `/`, `/app.js`, `/styles.css` и POST `/api/calculate`.
5. **Проверить вручную:** частичный объект → сохранение → перезапуск сервера → открытие; дополнение данных → новая версия; старая версия неизменна.
6. **Продолжить TASK-02:** индивидуальные источники/статусы, просмотр истории и остальные отложенные улучшения. Редактор норм и цен оставить в TASK-03, КП — в TASK-05.

После изменения контракта обновить `README.md`. Перед несовместимым изменением схемы хранения согласовать миграцию и сделать резервную копию базы. TASK-03–TASK-09 сейчас запускать не требуется.
