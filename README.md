# Локальное приложение ИВОК

Главный приоритет — **расчёт отопления и формирование сметы по отоплению**. Водоснабжение, канализация, каталог и материалы — сопутствующие подсистемы, которые помогают основной задаче. **Материалы в текущем этапе не входят в КП** (см. `Task.md`); стоимость формируется только по монтажным работам. Инженерная приёмка реальных примеров фиксируется отдельно — автоматические тесты не заменяют ручную приёмку.

Реализация **TASK-01**, локального этапа **TASK-02**, **TASK-03** и подэтапов A, B, C, D1, D2, D3, E, E2 **TASK-04** из `Task.md`:

- детерминированный расчёт отопления;
- карточки клиентов и объектов;
- сохранение версий расчётов в SQLite;
- источник и статус каждого входного и вычисленного параметра;
- веб-интерфейс и CLI расчётного ядра;
- каталог san-baza и ручной выбор материалов объекта с отдельными версиями;
- расчёт водоснабжения (точки ХВС/ГВС, рециркуляция-петля) и канализации (точки Ø50/Ø110, лежаки, стояки) со снимками цен;
- UI-вкладка `/santeh?objectId=...` для водоснабжения и канализации;
- миграция старой `calculations` (без `block`/`work_prices_json`) в новую схему с `block` и CHECK до `sewage`.

Авторизация, AI, внешние интеграции и автоматический подбор товаров пока не используются.

## Требования

- Node.js 22.13 или новее (для встроенного модуля SQLite);
- npm.

В окружении с `NODE_ENV=production` установите зависимости разработки явно:

```bash
npm install --include=dev
```

## Веб-приложение

Запустите локальный сервер:

```bash
npm run web
```

Откройте в браузере:

```text
http://127.0.0.1:3000
```

Сервер намеренно принимает подключения только с локального компьютера. Другой порт можно задать переменной `PORT`.

В интерфейсе можно:

1. создать карточку клиента и объекта — обязательны только имя клиента и адрес объекта; карточку можно сохранить без расчёта;
2. заполнить известные помещения и параметры; пустые поля остаются неизвестными, а не нулевыми;
3. указать общий источник и статус введённых параметров;
4. сохранить расчёт;
5. открыть сохранённый объект, отредактировать карточку и добавить новую версию расчёта;
6. посмотреть источник и статус каждого сохранённого параметра;
7. скачать исходные данные и отчёт в JSON.

**«Сохранить карточку»** сохраняет только данные клиента и реквизиты объекта. Изменения полей отопления и их метаданные эта кнопка не сохраняет.

**«Сохранить и рассчитать»** сохраняет параметры отопления и метаданные новой версией, даже если данных недостаточно для полного расчёта. Отдельного черновика параметров без расчёта пока нет.

В списке объектов отображается статус последнего расчёта или «Без расчёта». На экранах шириной до 640 px список по умолчанию свёрнут; кнопка «Показать объекты» открывает его. После выбора объекта список сворачивается.

По умолчанию база находится в `data/ivok.sqlite`. Путь можно изменить переменной `IVOK_DATABASE_PATH`. Каталог `data/` не сохраняется в Git.

Остановить сервер можно сочетанием `Ctrl+C`.

## HTTP API

| Метод и адрес | Назначение |
| --- | --- |
| `GET /api/objects` | Список сохранённых объектов |
| `GET /api/catalog?query=...&category=...&page=1` | Поиск сохранённых товаров, категории и страница из 50 позиций |
| `POST /api/objects` | Создать клиента и объект; первый расчёт можно передать необязательно |
| `GET /api/objects/:id` | Получить карточку, версии расчётов отопления, водоснабжения и канализации |
| `PATCH /api/objects/:id` | Изменить карточку клиента и объекта |
| `POST /api/objects/:id/calculations` | Добавить версию расчёта отопления |
| `POST /api/objects/:id/plumbing` | Добавить версию расчёта водоснабжения со снимком цен (`baseRevision`); 409 при устаревшей редакции |
| `POST /api/objects/:id/sewage` | Добавить версию расчёта канализации со снимком цен (`baseRevision`); 409 при устаревшей редакции |
| `GET /api/objects/:id/materials` | Объект, последняя комплектация и список её версий |
| `POST /api/objects/:id/materials` | Сохранить отдельную версию материалов по текущим ценам каталога |
| `GET /api/objects/:id/materials/:versionId` | Прочитать неизменяемую версию материалов |
| `GET /api/rules` | Прочитать семь действующих инженерных норм; только просмотр |
| `GET /api/works` | Прочитать 41 работу (35 отопления + 2 водоснабжения + 4 канализации), базовые цены, цену ИВОК, наценку и версию справочника |
| `PUT /api/works` | Атомарно сохранить базовые цены и наценку с проверкой версии |
| `POST /api/calculate` | Выполнить расчёт отопления без сохранения, с текущими ценами работ из SQLite |
| `POST /api/plumbing` | Выполнить расчёт водоснабжения без сохранения, с текущими ценами работ из SQLite |
| `POST /api/sewage` | Выполнить расчёт канализации без сохранения, с текущими ценами работ из SQLite |

Все основные сущности сохраняют `organization_id`. В локальном режиме используется одна системная организация `org-local`.

## Запуск расчёта через CLI

Из файла:

```bash
npm run calculate -- examples/heating-input.json
```

Через stdin:

```bash
cat examples/heating-input.json | npm run calculate
```

Команда печатает отчёт в stdout. Ошибка JSON или входного контракта печатается в stderr, код завершения — `2`.

## Расчёт водоснабжения (TASK-04, подэтапы A и B)

```bash
npm run calculate:plumbing -- examples/plumbing-input.json
cat examples/plumbing-input.json | npm run calculate:plumbing
```

Подэтап A: точки ХВС, ГВС и рециркуляции по фиксированной матрице приборов. Без стоимости, без трасс, без канализации.

Подэтап B: добавляет стоимость работ. Снимок цен передаётся флагом `--prices`:

```bash
npm run calculate:plumbing -- examples/plumbing-input.json --prices examples/plumbing-prices.json
```

Снимок цен — JSON-файл со полями:

- `revision` — неотрицательное целое (версия справочника);
- `waterHotPointRub` — базовая цена за одну точку ХВС+ГВС (`heating_water_point`);
- `recirculationPerMeterRub` — базовая цена за метр рециркуляции (`plumbing_recirculation`);
- `trapInstallRub` — базовая цена за штуку монтажа трапа (`plumbing_trap_install`);
- `markupPercent` — наценка; если не указана, берётся 45.

Без `--prices` отчёт содержит `costStatus: "impossible"`, `costSubtotalKopecks: null` и пустые `costLines`. Со снимком добавляются:

- строка «Монтаж точки водоснабжения ХВС и ГВС» — `hotWaterPoints × ivokPriceRub(waterHotPointRub, markup)`;
- отметки `PLUMBING_COST_RECIRCULATION_DEFERRED` и `PLUMBING_COST_TRAPS_DEFERRED` в `costAppliedRules` (длина трассы и количество трапов — подэтап D);
- `costSubtotalKopecks` — копейка-точная сумма по строкам.

Деньги считаются через `lineTotalKopecks` (точная арифметика до копейки, без бинарного умножения). Цена ИВОК = `ivokPriceRub(базовая, наценка)` — потолок рубля, без копеек. Чистое ядро: `calculatePlumbing(input, workPrices?)`.

### Канализация (TASK-04, подэтап D1)

CLI:

```bash
npm run calculate:sewage -- examples/sewage-input.json
npm run calculate:sewage -- examples/sewage-input.json --prices examples/sewage-prices.json
```

Без `--prices` отчёт содержит `costStatus: "impossible"`, `costSubtotalKopecks: null` и пустые `costLines`. Со снимком добавляются строки:

- «Монтаж точки канализации Ø50 (вкл. трап)» — `points50 × ivokPriceRub(sewagePoint50Rub, markup)`, где `points50` — сумма Ø50-приборов + `trapCount` (если задан);
- «Монтаж точки канализации Ø110» — `points110 × ivokPriceRub(sewagePoint110Rub, markup)`;
- «Прокладка канализационного лежака» — `Σ lengthM (по не-выполненным лежакам) × ivokPriceRub(sewerMainPerMeterRub, markup)` — только если в `sewerMains` есть хотя бы один лежак с ненулевой длиной и WorkId `sewer_main` не в `sewer.alreadyExecuted`.

Монтаж трапа **входит в цену точки Ø50** (соглашение D3): отдельной строки `plumbing_trap_install` в `costLines` нет. `trapCount` в `SewageInput.sewer` сохраняется для инженерного отчёта; если `trapCount === null` и в канализации есть приборы со стоком в пол (душ), выдаётся предупреждение `SEWAGE_TRAP_COUNT_MISSING`.

Снимок цен — JSON-файл со полями:

- `revision` — неотрицательное целое (версия справочника);
- `sewagePoint50Rub` — базовая цена за одну точку Ø50 (`sewage_point_50`, в неё же заложен монтаж трапа);
- `sewagePoint110Rub` — базовая цена за одну точку Ø110 (`sewage_point_110`);
- `sewerMainPerMeterRub` — базовая цена за метр лежака (`sewer_main`);
- `markupPercent` — наценка; если не указана, берётся 45.

**Правила D3 (согласованные):** в канализации используются только Ø50 и Ø110. Ø100 не применяется (автопересчёт не выполняется). Коллекторы канализации не считаются. Рециркуляция у канализации отсутствует — `hasRecirculation` остаётся только в `PlumbingInput` (ГВС).

Деньги — те же правила, что в водоснабжении: `lineTotalKopecks` (точная арифметика до копейки), `ivokPriceRub` (потолок рубля). Чистое ядро: `calculateSewage(input, workPrices?)`.

Считается по фиксированной матрице стоков:

- Ø110 — унитаз;
- Ø50 — раковина, мойка кухонная, душ, ванна, гигиенический душ, стиральная машина, посудомойка.

**Лежаки (TASK-04, подэтап D2).** Поле `sewerMains: SewerMain[]`, где `SewerMain = { id, fromRoomIds: string[], lengthM: number, alreadyExecuted: boolean }`. Каждая комната с канализационными приборами должна быть упомянута хотя бы в одном лежаке — иначе валидация отвергает вход. Длина в `lengthM` — явно заданная; `0` допустим (лежак есть, но без метража в смете). `alreadyExecuted: true` исключает лежак из сметы, но `lengthM` продолжает идти в `report.lengthM` (полный метраж). В отчёте появляются правила `SEWAGE_MAIN_FROM_ROUTES`, `SEWAGE_MAIN_ALREADY_EXECUTED`, `SEWAGE_MAIN_INPUT` и предупреждение `SEWAGE_MAIN_MISSING` (если `sewerMains` пуст).

Вход:

```json
{
  "sewer": { "trapCount": 1, "alreadyExecuted": [] },
  "plumbing": { "rooms": [...], "hotWaterSource": "two_loop_boiler" }
}
```

- `sewer.trapCount` — `null` или отсутствие душовых приборов не выдаёт предупреждения; при наличии душа и `trapCount === null` выдаётся `SEWAGE_TRAP_COUNT_MISSING`. Любое `trapCount > 0` увеличивает количество точек Ø50 в смете (монтаж трапа входит в цену точки);
- `sewer.alreadyExecuted` — массив `WorkId` (идентификаторы работ из `workDefinitions`). Уже выполненные закладные исключаются из сметы, в `appliedRules` добавляется `SEWAGE_ALREADY_EXECUTED`.

Каталог коллекторов и автопересчёт Ø100→Ø110 **не предусмотрены** (D3): в канализации только Ø50 и Ø110, монтаж трапа входит в цену точки, рециркуляция у канализации отсутствует. Сохранение в SQLite, HTTP и UI подключены; в смете канализации также учитываются **фановые стояки** (`sewer.standpipes`, работа `sewage_standpipe`, 3000 ₽/шт; E2).

### Вкладка «Сантехника и канализация» (подэтапы E, E2)

Из карточки объекта открывается `/santeh?objectId=<id>` в новой вкладке. Страница содержит две секции: водоснабжение и канализация. Кнопка «Посчитать воду» отправляет `POST /api/plumbing`, «Посчитать канализацию» — `POST /api/sewage`; «Сохранить версию» — `POST /api/objects/:id/plumbing` или `POST /api/objects/:id/sewage` со снимком `workPrices` и `baseRevision`. При устаревшей редакции — 409, обновите страницу и повторите.

**Водоснабжение.** Модель UI — «комната → приборы» (TaskCheck P1). На странице список комнат с возможностью добавить новую. Внутри комнаты — приборы (тип из выпадающего списка, количество, длина трассы к прибору, комментарий). `roomId` подтягивается из последней версии отопления (`/api/objects/:id → calculations[0].input.rooms[].id`); если отопления нет, комнаты добавляются вручную кнопкой «+ Добавить комнату» с автогенерацией `room-N`. Рециркуляция ГВС задаётся на уровне комнаты (`hasRecirculation: true/false/null`); петля рециркуляции (`recirculationLengthM`) — общее поле внизу формы. Если рециркуляция включена хотя бы в одной комнате, а длина петли не задана, статус блока — `requires_engineer_review` с предупреждением `PLUMBING_RECIRCULATION_LENGTH_MISSING`. Длины трасс к приборам (`fixture.lengthM`) сохраняются в снимке версии для будущего расчёта (D+); в текущей смете они не участвуют.

**Канализация.** Лежаки выбирают `roomId` из комнат водоснабжения (TaskCheck P1 — лежаки привязаны к реальным комнатам, а не к типам приборов). В UI для каждого лежака: чекбоксы по комнатам с канализационными приборами + длина + «уже выполнено». Ниже — количество стояков (шт), `trapCount`, уже выполненные закладные. После расчёта — метрики: `Ø50` точек, `Ø110` точек, длина лежаков, стоимость (отдельно статус расчёта и статус стоимости). Если есть канализационные приборы и не все комнаты покрыты лежаками, расчёт вернёт `requires_engineer_review` с `missingParameters` и предупреждением `SEWAGE_MAIN_INCOMPLETE` (P2, `TaskCheck.md`). Сервер не подставляет лежаки автоматически. Монтаж трапа входит в цену точки Ø50, отдельной строки в смете нет. Ø100 не используется (D3). Коллекторы канализации не считаются.

**Контракт E2:**

- `PlumbingInput.recirculationLengthM: number | null` — длина петли рециркуляции ГВС одной трубой. Если `null` или 0 — стоимость не считается. При `hasRecirculation === true` хотя бы в одной комнате и `recirculationLengthM` не задана — блок получает `costStatus: requires_engineer_review` и предупреждение `PLUMBING_RECIRCULATION_LENGTH_MISSING`.
- `PlumbingFixtureEntry.lengthM: number | null` — длина трассы подачи к прибору. Сохраняется в снимке версии; в текущей смете не участвует (D+).
- `SewageInput.sewer.standpipes: number` — количество фановых стояков (целое ≥ 0). В смете — строка `sewage_standpipe` × `standpipes` × цена ИВОК.
- Справочник работ (`/api/works`) — 41 позиция: 35 отопления + 2 водоснабжения + 4 канализации (`sewage_point_50`, `sewage_point_110`, `sewer_main`, `sewage_standpipe`).
- Старые сохранённые версии (без `recirculationLengthM`, `fixture.lengthM`, `sewer.standpipes`) читаются без миграции: недостающие поля = `null`/`0`, старые сметы не пересчитываются.

### Статусы расчёта и стоимости

В отчётах водоснабжения и канализации присутствуют **два разных статуса**:

- `report.status` — статус расчёта блока (точки, лежаки, стояки). `impossible` означает, что вход нельзя посчитать по согласованным правилам (например, `sewer.sewerMains` пуст).
- `report.costStatus` — статус стоимости. `impossible` означает, что снимок цен не передан или сумма неизвестна; `requires_engineer_review` — расчёт возможен, но требуется решение инженера (например, включена рециркуляция без длины петли).

В UI `/santeh` оба статуса отображаются отдельными бейджами. `null` стоимости показывается как «Не рассчитано» с пояснением причины; `0` ₽ отображается явно, не как `null`. Это поведение зафиксировано в `TaskCheck.md` (P1) и покрыто регрессионными тестами.

### Частичный расчёт канализации (TaskCheck P2)

`parseSewageInput` **не отвергает** вход, если канализационные комнаты не покрыты лежаками. В этом случае `calculateSewage` возвращает:

- `status: requires_engineer_review`,
- `warnings` содержит код `SEWAGE_MAIN_INCOMPLETE` со списком непокрытых комнат,
- `missingParameters` содержит пути `sewer.sewerMains[room=…]`,
- `costStatus: requires_engineer_review` — стоимость не считаем полной, пока инженер не закроет покрытие.

Никаких автогенерируемых лежаков или приблизительных длин. Покрытие можно закрыть, добавив лежак с нужным `fromRoomIds` или убрав канализационные приборы.

### Сохранение через HTTP (подэтап C)

```bash
# Создать объект
curl -X POST http://127.0.0.1:3000/api/objects \
  -H "content-type: application/json" \
  -d '{"client": {"name": "Иванов"}, "object": {"address": "Лесная 1"}}'

# Снимок цен (получить текущий)
curl http://127.0.0.1:3000/api/works

# Расчёт без сохранения
curl -X POST http://127.0.0.1:3000/api/plumbing \
  -H "content-type: application/json" \
  -d @examples/plumbing-input.json

# Сохранение версии со снимком цен
curl -X POST http://127.0.0.1:3000/api/objects/<id>/plumbing \
  -H "content-type: application/json" \
  -d '{
    "input": { ... },
    "parameterMetadata": [],
    "workPrices": { "baseRevision": 0, "revision": 0,
      "waterHotPointRub": 2000, "recirculationPerMeterRub": 1000,
      "trapInstallRub": 2000, "markupPercent": 45 }
  }'
```

`POST /api/objects/:id/plumbing` возвращает 201 c записью `SavedPlumbingCalculation`. Если редакция справочника сменилась — 409. Несуществующий объект — 404. Поле `plumbingCalculations` в `GET /api/objects/:id` — массив сохранённых версий, отсортированный по дате. Старые heating-расчёты не затираются.

## TASK-03: каталог san-baza

Источник материалов — `san-baza.ru`. Файл `san-baza.xlsx` получен парсингом сайта, а не выгрузкой 1С. Скрипта парсинга в проекте пока нет.

Первый подэтап — проверка локального XLSX **без записи в SQLite**:

```bash
npm run catalog:check -- san-baza.xlsx
```

Команда читает лист `Каталог`: заголовки в строке 4 — `Категория`, `Название`, `Артикул`, `Цена, ₽`, `Единица`, `URL`; товары начинаются со строки 5. Пустые строки пропускаются. Другой порядок колонок или дополнительные непустые колонки требуют изменения формата, а не угадываются автоматически.

- Категория, название и единица — непустой текст. Пробелы по краям текстовых значений убираются; единицы не пересчитываются и не переименовываются.
- Артикул — текст или пустая ячейка. Ведущие нули сохраняются. Числовой артикул отмечается ошибкой, поскольку потерянные нули восстановить нельзя. Повторяющиеся артикулы допустимы: это не ключ товара.
- Цена — числовая ячейка с конечным значением ≥ 0 или пустая ячейка. Текстовые цены не преобразуются автоматически. Отсутствующая цена остаётся `null`; нулевая остаётся `0`. Обе ситуации отражаются отдельными счётчиками и не означают разрешение считать товар бесплатным.
- URL — HTTPS-ссылка на `san-baza.ru/catalog/` без параметров, фрагмента и учётных данных. Дубли URL отмечаются во всех конфликтующих строках; программа не выбирает одну из них автоматически. Категория не выводится из пути URL.
- Дата из заголовка не считается подтверждённой датой прайса. Характеристики, производитель и наличие не извлекаются из названий.

Результат — JSON-сводка: `rowCount`, `validRowCount`, `formatValid`, ошибки `issues` с исходными номерами строк и колонками. Счётчики `missingArticleCount`, `missingPriceCount`, `zeroPriceCount` и `repeatedArticleCount` относятся к строкам без ошибок; последний считает разные повторяющиеся артикулы после удаления краевых пробелов. Полный список товаров в CLI не печатается. Для чистого JSON без служебного вывода npm после сборки используйте `node dist/src/catalog-cli.js san-baza.xlsx`.

Код завершения: `0` — формат проверен; `2` — ошибки строк, структуры файла или аргументов; `1` — ошибка файловой системы. `formatValid` не подтверждает актуальность цен или инженерную пригодность товара. Чтение формул использует сохранённые значения XLSX, но не вычисляет их; проверка предназначена для локальной выгрузки, не для публичной загрузки произвольных файлов.

### Импорт и журнал

Согласован **частичный импорт**: корректные строки сохраняются, ошибочные пропускаются и попадают в журнал.

```bash
npm run catalog:import -- san-baza.xlsx
npm run catalog:log
npm run catalog:log -- ID_ИМПОРТА
```

`catalog:import` пишет в `data/ivok.sqlite` или путь из `IVOK_DATABASE_PATH`, как веб-приложение. Перед первым импортом в существующую рабочую БД сделайте резервную копию; при копировании файла SQLite остановите сервер. Добавляются таблицы `catalog_products` и `catalog_imports`; таблицы карточек и сохранённые отчёты не изменяются. `catalog:log` открывает БД только для чтения и не создаёт отсутствующий файл. До первого импорта журнал недоступен.

- Ключ обновления — организация + источник + URL (в представлении `new URL(...).href`). Артикул не используется как ключ. Идентификатор существующего товара сохраняется.
- Корректная строка заменяет текущие поля товара, включая пустой артикул или цену `null`. Нулевая цена сохраняется отдельно от неизвестной и не является инженерным подтверждением бесплатного товара.
- Пропущенная ошибочная строка не меняет ранее сохранённый товар. Отсутствующие в новом файле товары также не удаляются. При повторяющемся URL пропускаются все строки с этим URL; старая позиция остаётся без изменений.
- Товары и журнал сохраняются одной транзакцией. Сбой SQLite откатывает все изменения этого импорта, а не выдаётся за ошибку отдельной строки.
- Если все строки ошибочны, сохраняется только журнал с нулём загруженных строк. Если файл нечитаем, отсутствует лист/заголовок или каталог пуст, запись не начинается и ошибка показывается в stderr без записи в журнал.
- Журнал содержит имя файла, источник, время загрузки, количество новых/обновлённых/пропущенных строк, счётчики неизвестных данных и отдельный массив `issues`. Один пропущенный ряд может иметь несколько ошибок. Повторный запуск создаёт новую запись журнала; старые записи не меняются. `updatedRows` включает повторно загруженные позиции даже без изменения значений.
- В товаре сохраняется ссылка `lastImportId` на последнюю успешную загрузку этой позиции. Время загрузки не является подтверждённой датой цены сайта. Исторические версии всех полей товаров пока не сохраняются; журнал хранит сводку и ошибки.

Коды завершения **импорта**: `0` — все строки загружены; `3` — журнал сохранён, ошибочные строки пропущены (корректные уже записаны, если они были); `2` — ошибка аргументов или формата файла, импорт не начат; `1` — ошибка чтения/записи. Журнал печатается в stdout как JSON. Для чистого JSON после сборки: `node dist/src/catalog-storage-cli.js import san-baza.xlsx` или `node dist/src/catalog-storage-cli.js log [ID_ИМПОРТА]`.

### Веб-каталог и поиск

После запуска `npm run web` откройте `http://127.0.0.1:3000/catalog` (с учётом вашего `PORT`). На главной странице есть ссылка «Каталог материалов — в новой вкладке»: несохранённая карточка остаётся в исходной вкладке.

- Поиск по части названия или артикула без учёта регистра, включая кириллицу. Нажмите «Найти» или Enter; символы `%`, `_` и кавычки ищутся буквально, не как шаблон SQL.
- Категория выбирается из сохранённого каталога, фильтруется точным совпадением и применяется вместе с поиском. Смена категории сразу запускает поиск. «Сбросить фильтры» возвращает весь каталог на первую страницу.
- На странице не более 50 позиций, порядок — по имени без учёта регистра, затем URL. «Назад» и «Далее» переключают страницы. Устаревший ответ поиска не заменяет более свежий.
- Карточка показывает название, категорию, артикул, цену, исходную единицу, источник и время загрузки. Ссылка на товар открывается в новой вкладке. `null` отображается как «Цена не указана», `0` — как нулевая цена с пометкой «требует проверки».
- До первого импорта показывается пустой каталог; просмотр не создаёт таблицы каталога и не записывает данные. После CLI-импорта нажмите «Найти» — перезапуск сервера для обновления товаров не требуется.
- Ошибка загрузки отображается отдельно; старые результаты скрываются. Нажмите «Найти» для повтора. Интерфейс адаптирован к узким экранам.

API возвращает `products`, `total` (по фильтрам), `catalogTotal` (весь доступный каталог), `categories`, `page`, `pageSize`, `latestImportAt`. `latestImportAt` — ISO-строка самой свежей записи `catalog_imports` для организации, либо `null`, если импорт ещё не выполнялся. В шапке `/catalog` отображается как «База обновлена: …»; если строка отсутствует, блок скрыт. `query` ограничен 200 символами, `category` — 1000; `page` — положительное целое с безопасным смещением. По умолчанию фильтры пустые, страница — 1. Повторяющиеся/неизвестные параметры и неверные значения дают HTTP 400. Для программно внедрённого хранилища карточек без SQLite каталог возвращает HTTP 503, а не подключается к другой базе. В обычном локальном запуске используется та же SQLite, что и для карточек, но соединение каталога открыто только для чтения.

Загрузка Excel через браузер пока не реализована. Инженерные нормы доступны для просмотра на `/rules`; их редактирование отложено по решению пользователя. Полный справочник из 35 работ раздела «Отопление» с базовыми ценами, наценкой и ценами ИВОК доступен на `/works`. Выбранные материалы сохраняются отдельно и не участвуют в инженерном расчёте отопления. Названия и характеристики не исправляются автоматически: например, текущая выгрузка содержит три товара с названием «1» (строки 251–253), требующие уточнения источника.

XLSX читает `read-excel-file` (MIT), версия закреплена в `package.json`. Синтетические тестовые XLSX лежат в `test/fixtures/catalog-*.xlsx`; их генератор `test/fixtures/generate-catalog-fixtures.py` использует только стандартную библиотеку Python. Для запуска тестов Python не нужен.

### Материалы объекта

После обновления кода перезапустите локальный сервер (`npm run web`) и обновите страницу. Сначала сохраните несохранённые данные. Для первого использования новой функции в рабочей базе рекомендуется резервная копия SQLite.

1. Откройте или сохраните карточку объекта. Под карточкой находится блок «Товаров отобрано»: нажмите «Добавить материалы» или «Перейти в материалы». Подбор откроется в новой вкладке.
2. На `/catalog?objectId=...` найдите товар и нажмите «Добавить в материалы объекта». Введите положительное количество в исходной единице; количество не подставляется автоматически. Дробные количества допустимы, автоматического пересчёта упаковок или единиц нет.
3. Повторный выбор того же товара не дублирует строку — измените её количество. Кнопка «Убрать» меняет только черновик.
4. Нажмите **«Сохранить материалы»**. Сервер заново читает все выбранные товары и цены из текущего каталога и создаёт новую версию. Цены в черновике информационные; фактические цены закрепляются в сохранённой версии. Можно сохранить повторно без изменения количества, чтобы получить новую версию по свежим ценам.
5. В разделе «Сохранённые версии материалов» откройте нужную версию. Это просмотр снимка, не замена текущего черновика. «Загрузить последнюю версию» заменяет черновик; при несохранённых изменениях требуется подтверждение.

На главной странице блок **«Товаров отобрано — N позиций»** свёрнут по умолчанию и снова сворачивается при смене объекта. Кнопка перехода находится снаружи и доступна без раскрытия. Внутри — только просмотр последней сохранённой версии: номер/дата, товары, количества, единицы и цены каталога. Блок известной стоимости и счётчики «без цены / с нулевой ценой» в текущем этапе не отображаются: материалы не входят в КП. Для пустой комплектации показано «Товары пока не отобраны»; до сохранения карточки — просьба сначала сохранить объект.

В шапке `/catalog` отображается «База обновлена: …» с ISO-датой самой свежей записи `catalog_imports` (поле `latestImportAt` в `/api/catalog`). Если импорта не было, строка скрыта.

При выборе объекта, сохранении карточки и возвращении в главную вкладку обновляется только блок материалов. Несохранённые поля клиента/отопления, помещения и результат расчёта не сбрасываются. Раскрытие блока для того же объекта сохраняется. Черновик из другой вкладки не показывается: сначала нажмите там «Сохранить материалы». Ошибка чтения отображается отдельно с кнопкой «Повторить загрузку», а не маскируется пустой комплектацией. Устаревшие ответы не подменяют материалы текущего объекта.

Для этой доработки достаточно обновить страницу после сохранения текущего ввода; новые маршруты и перезапуск сервера не нужны. Последняя комплектация не привязана к версии отчёта отопления и не прибавляется автоматически к стоимости работ.

Снимок содержит количество, название, категорию, артикул, единицу, цену, источник/URL и ID импорта каждого товара. Прежние версии не пересчитываются после обновления прайса. Если исходная единица товара изменилась, сохранение останавливается: удалите строку из черновика, выберите товар заново и проверьте количество.

Суммы строк (`lineTotalKopecks`, `knownTotalKopecks`, счётчики `unpricedCount` / `zeroPriceCount`) сервер продолжает считать и сохранять в снимке для будущего использования. В текущем этапе КП и расчёт отопления их не читают: материалы будут прикручены позднее. Неизвестная цена даёт `lineTotalKopecks: null`, а не ноль. Округление до копейки (половина вверх) и проверка переполнения остаются в силе.

POST принимает только `{ baseVersionId, items: [{ productId, quantity, expectedUnit }] }`. `baseVersionId` — ID последней открытой версии или `null` до первого сохранения. Цены, названия и суммы от браузера не принимаются. Не более 500 строк; повторяющиеся ID и неверные количества дают HTTP 400. Неизвестный объект/версия — 404; устаревшая вкладка или изменение единицы — 409 без потери черновика. При потере связи сначала загрузите последнюю версию и проверьте, было ли сохранение выполнено.

Версии хранятся в новой таблице `object_material_versions`; она создаётся внутри транзакции при первом успешном сохранении. Просмотр до сохранения не создаёт таблицу. Запись не меняет карточку, каталог или версии расчётов отопления. Пустую комплектацию можно сохранить после подтверждения, старые версии при этом остаются в истории. Черновик живёт только в открытой вкладке; при уходе с несохранёнными изменениями браузер запрашивает подтверждение, автоматического восстановления черновика после закрытия нет.

### Справочник работ

На главной странице ссылка **«Справочник работ — в новой вкладке»** открывает `/works`. Справочник содержит все 35 строк раздела «ОТОПЛЕНИЕ» листа «Отопление» из файла «Смета работ.xlsx». Другие разделы и листы пока не импортируются. Названия перенесены из исходника; для строки «Штробление стен» отсутствующая базовая цена задана как 0 по решению пользователя. Пустая единица в исходной таблице не была выдумана: сейчас для всех позиций используется нейтральное обозначение «ед.». Цены из PDF демонстрационные и не служат источником данных.

Базовая цена редактируется. Над таблицей задаётся общая наценка ИВОК — 45% по умолчанию. Цена ИВОК за единицу отображается без округления строки; при расчёте будущей строки нужно будет сначала умножить базовую цену на количество, начислить процент, затем округлить итог вверх до целого рубля. Такой расчёт строк пока не реализован, поскольку ввод количества и КП отложены. Базовые цены «Монтаж водяных теплых полов» и «Монтаж пеноплекса» используются в текущих веб-расчётах отопления без ИВОК-наценки.

Текущие позиции:

| Раздел | Число работ |
| --- | ---: |
| Отопление | 35 |
| Водоснабжение | 2 |
| Канализация (D1, D2, E2) | 4 |

Введите базовые цены и наценку, затем нажмите **«Сохранить цены»**. Базовые цены допускают неотрицательные значения с точностью до копейки; пустое поле не означает ноль. Нулевая цена применяемой работы при положительной площади ТП даёт предупреждение `WORK_ZERO_PRICE_REVIEW` и как минимум `requires_engineer_review`. Переполнение цены или результата отклоняется.

Сохранённые цены монтажа ТП и утеплителя применяются ко всем **новым веб-расчётам**: предварительному, первому расчёту объекта и последующим версиям. Уже открытый отчёт сам не пересчитывается: нажмите «Сохранить и рассчитать», когда нужна новая версия. Изменение справочника не сбрасывает форму главной вкладки и не меняет старые JSON-отчёты. Остальные три работы пока справочные: автоматические расчёты водоснабжения и канализации не добавлены.

Новый веб-отчёт содержит `workPrices: { revision, floorHeatingRubPerM2, insulationRubPerM2 }`. Это снимок применённых расценок, а не ссылка на изменяемые настройки. Коды `FH_INSTALLATION_PRICE` и `FH_INSULATION_PRICE` описывают фактические цены; суммы округляются по каждой работе до копейки в десятичной арифметике. Версия цен не является версией всех инженерных правил: редактор норм остаётся отдельной задачей.

Чистый модуль поддерживает `calculateHeating(input, workPrices?)`. Вызов без второго аргумента и автономный CLI сохраняют прежние нормы из `src/config.ts` и формат отчёта; CLI не подключает SQLite и не использует цены из веб-редактора. Для воспроизведения нового веб-расчёта передавайте его `input` и сохранённый `workPrices`.

`GET /api/works` возвращает `{ revision, markupPercent, items }`, где у каждой работы есть `id`, `name`, `unit`, `priceRub` (базовая цена), `ivokPriceRub`, `appliedToHeating`. `PUT` принимает `{ baseRevision, markupPercent, prices: [{ id, priceRub }] }` с 35 уникальными ID из исходного отопительного листа. Имена/единицы менять нельзя. Наценка — от 0 до 10000 процентов; пустые, отрицательные и превышающие безопасный денежный диапазон значения отклоняются. Неверный ввод — 400, устаревшая версия — 409. При ошибке черновик сохраняется в форме; «Загрузить актуальные цены» запрашивает подтверждение отмены правок. Автоматического восстановления черновика после закрытия вкладки нет.

Стартовые значения версии 0 читаются без записи в БД. Первое изменение создаёт `work_price_versions` в транзакции. Версии привязаны к `organization_id`; новое JSON-хранение сохраняет базовые цены и наценку, а чтение прежнего формата с пятью ценами восстанавливает старые цены двух отопительных работ и добавляет остальные работы по значениям книги. Повторное сохранение тех же базовых цен и наценки не создаёт новую версию. При потере ответа проверьте актуальные цены перед повторным редактированием. Новые backend-маршруты требуют перезапуска локального сервера; рабочую БД при разработке не изменяем.

### Просмотр правил расчёта

Ссылка **«Правила расчёта — в новой вкладке»** на главной открывает `/rules`. Здесь показаны семь действующих норм с единицами и пояснениями: расход трубы 6 м/м², стандартный контур 80 м, исключение до 90 м, максимум 12 контуров на коллектор, базовая мощность радиаторов 100 Вт/м², снижение при наличии ТП 30%, стандартная высота потолков до 3,2 м.

Это **только просмотр**: редактируемых полей и кнопки сохранения нет. Источник значений — `src/config.ts` работающего сервера, используемый калькулятором; в браузере нет собственной копии норм. Страница не создаёт настройки, версии или записи в БД, не меняет расчёты и не сбрасывает ввод главной вкладки. Показаны текущие правила сервера, а не исторический снимок конкретного отчёта. Цены остаются отдельно в `/works`.

`GET /api/rules` возвращает `{ readOnly: true, items: [{ id, name, value, unit, description }] }`. Методы записи отклоняются с 405 и `Allow: GET`. При ошибке или неполном ответе значения не подставляются: отображаются сообщение и «Повторить загрузку». Для включения нового маршрута нужен согласованный перезапуск локального сервера.

## Входной контракт расчёта

| Поле | Тип | Назначение |
| --- | --- | --- |
| `houseAreaM2` | положительное число или `null` | Общая площадь дома |
| `houseCeilingHeightM` | положительное число или `null`, необязательно | Высота потолков дома по умолчанию для помещений |
| `rooms` | массив | Можно оставить пустым, если отопление не описано |
| `heatSource` | `gas \| electric \| solid_fuel \| pellet \| unknown` | Источник отопления |
| `availableElectricPowerKw` | число или `null` | Доступная электрическая мощность |
| `residents` | целое ≥ 0 или `null` | Количество жильцов |
| `baths` | целое ≥ 0 или `null` | Количество ванн |
| `showers` | целое ≥ 0 или `null` | Количество душей |
| `includeIndirectWaterHeater` | boolean или `null` | Нужен / не нужен / неизвестно |
| `circuitLengthM` | положительное число или `null`, необязательно | В форме по умолчанию неизвестна; более 80 до 90 м требует проверки, более 90 м невозможно |

Каждое помещение содержит обязательные `id`, `name` и параметры `areaM2`, `ceilingHeightM`, `hasStandardWindows`, `hasPanoramicWindows`, `floorHeatingAreaM2`, `hasRadiator`. Числа и логические параметры могут быть `null`. Для радиаторов `true` означает «есть / нужен», `false` — «нет / не нужен», `null` — «неизвестно».

Пропущенные расчётные параметры нормализуются в `null`, пропущенные помещения — в пустой массив, источник тепла — в `unknown`. Пустая строка в JSON не считается числом. В форме пустая длина контура передаётся как `null`: труба и работы рассчитываются, а для количества контуров требуется длина. Только пропущенное поле в старом JSON использует норму 80 м для обратной совместимости. Источник по умолчанию не указан (`""`); это не означает «Инженер».

### Высота потолков и количества в помещениях

- В форме задайте «Высота потолков дома». В каждой новой комнате включено «Как в доме»: её высота отображается и обновляется при изменении высоты дома.
- Снимите «Как в доме», чтобы задать другую высоту комнаты. Индивидуальная высота не меняется при изменении дома. Пустая высота остаётся неизвестной; значение 2,8 м или другое стандартное значение не подставляется.
- Во входе комнаты `useHouseCeilingHeight: true` означает наследование. Сервер берёт `houseCeilingHeightM` и сохраняет эффективное значение в прежнем поле `ceilingHeightM`. `false` означает индивидуальную высоту, включая неизвестную `null`. Если признак пропущен, старая явно заданная высота сохраняется; пустая высота наследует значение дома, если поле высоты дома передано.
- Новые необязательные поля комнаты: `standardWindowCount`, `panoramicWindowCount`, `radiatorCount`. Это неотрицательные безопасные целые числа или `null`. `0` — нет элементов, `null` — количество неизвестно. Старое «есть» не преобразуется в «1 шт.».
- Ввод количества автоматически меняет признак наличия в форме. Если известно только наличие, оставьте количество пустым и выберите «Есть». В JSON известное количество задаёт соответствующий булев признак, если он неизвестен/пропущен; противоречивое сочетание числа и явного признака отклоняется.
- Высота свыше 3,2 м и наличие панорамных окон по-прежнему требуют инженера. Количество окон не вводит новых коэффициентов теплопотерь. Мощность радиаторов остаётся **суммарной для комнаты**, не делится автоматически между приборами. Количества сохраняются в версиях и JSON для последующего подбора и расчёта материалов.
- Старые JSON и отчёты без новых полей поддерживаются без миграции или пересчёта сохранённых версий.

### Частичный расчёт

Каждый блок рассчитывается независимо при достаточных данных. Недостаток данных даёт ему статус `impossible` и список путей `missingParameters`; неизвестные результаты остаются `null`. Остальные блоки продолжают рассчитываться. В одном блоке также могут оставаться известные результаты: например, труба и работы по ТП при неизвестном количестве смесительных узлов.

Старые полные JSON продолжают поддерживаться, сохранённые версии отчётов не пересчитываются при чтении. На новой карточке нет вымышленных помещений и предзаполненных исходных данных. Карточку без расчёта по-прежнему можно сохранить.

Суммы — **стоимость известных работ** (монтаж ТП и укладка утеплителя), не полная стоимость отопления. Цены материалов не заданы: материалы не считаются бесплатными. Неопределённый бойлер не является выбранным товаром.

## Статусы

Статусы расчёта:

- `calculated` — применены известные правила;
- `requires_engineer_review` — правило неполное или требуется инженерное решение;
- `impossible` — входное сочетание нельзя рассчитать по допустимым правилам.

Статусы проверки введённых параметров: `unverified`, `confirmed`, `requires_engineer_review`. Источники: `client`, `engineer`, `project_document` или пустое значение (не указан). Источник и подтверждение независимы.

Вычисленные параметры получают источник `calculation` и статус соответствующего расчётного блока. `calculated` означает выполнение расчёта по правилам, а не утверждение инженером.

Сейчас общий источник и статус применяются ко всем полям новой версии. Индивидуальное редактирование метаданных, выбор старых версий в интерфейсе, защита несохранённых изменений и выбор существующего клиента отложены до отдельного согласования.

Общий статус отчёта равен самому строгому статусу вложенных результатов. Отчёт также содержит коды применённых правил, предупреждения и ошибки.

## Принятые ограничения

- Приложение предназначено только для локальной проверки. Перед внешним размещением нужна авторизация.
- SQLite подходит для текущего однопользовательского режима. Доступ к данным отделён интерфейсом репозитория для последующего перехода на PostgreSQL.
- Площадь помещений может быть меньше площади дома: допускаются ещё не внесённые помещения.
- Панорамное окно или потолок выше 3,2 м запрещает автоматический расчёт мощности радиатора в этом помещении.
- Наличие бойлера косвенного нагрева переводит предварительный выбор мощности котла на проверку инженера.
- Для твердотопливного и пеллетного источника ТЗ не задаёт таблицу мощности, поэтому решение принимает инженер. Неизвестный источник — недостающий параметр для выбора котла.
- Материалы котельной, трубы, фитинги и конкретные товары не рассчитываются: этих правил нет в ТЗ версии 1.0.
